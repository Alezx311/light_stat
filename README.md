# Light Stat · карта світла по підгрупах

**Сайт:** https://alezx311.github.io/light_stat/

Карта адрес і історія світла для підгруп Telegram-каналу [«Підгрупи 6.2»](https://t.me/subgroups62) (Біличі, Академмістечко, Святошин). Перевірка каналу запланована кожні 5 хвилин; GitHub Actions може затримувати або пропускати запуски.

- **Карта першою.** 361 адреса забарвлена за станом своєї підгрупи; адреса з двома вводами має дві половинки. Клік відкриває підгрупи адреси, час останньої зміни стану та смугу за 24 години.
- **Усі підгрупи одразу.** Стан зараз і з якого часу; смуга за 24 години або 7 днів; частка часу зі світлом за тиждень. Наведення на рядок підсвічує адреси підгрупи на карті.
- **Пошук** за адресою або назвою підгрупи.
- **Деталі підгрупи** (`#sg=sg30`): календар «день × година» за 30 днів, вимкнення, найдовше відключення, список адрес.
- **[Розширена аналітика](https://alezx311.github.io/light_stat/explore.html)**: весь архів, порівняння, CSV, імпорт власних JSON.

Стан — це повідомлення каналу про підгрупу, а не вимірювання в кожному будинку. Якщо канал не перевірено 15 хвилин, карта, список, пошук і деталі показують «Стан невідомий». Підгрупи, що мовчать понад 30 днів, також невідомі. Історія зберігається незалежно від свіжості поточного стану.

## Як оновлюються дані

~~~text
GitHub Actions, кожні 5 хвилин (:02, :07, …, :57; можливі затримки)
  npm test
  tools/fetch-telegram.js   https://t.me/s/subgroups62 → data/events.json (лише нові пости)
  commit data/events.json, якщо з’явилися нові пости
  tools/build-site.js       → _site/ (+ data/summary.json) → GitHub Pages
~~~

- `data/events.json` — нормалізований журнал подій (schemaVersion 1), одна подія на рядок. `observedUntil` — час останньої успішної перевірки каналу.
- `data/addresses.json` — знімок прив’язки адрес до підгруп з [мапи відключень](https://eh-map.napruha.top/) того ж каналу. Містить координати, під’їзди, другий ввід, чергу ДТЕК і полігони кварталів. Оновлюється **лише вручну**: `node tools/import-eh-map.js <збережена-сторінка.html>`. robots.txt сайту забороняє автоматичний збір, тому з CI цей скрипт не запускається.
- Відкрита сторінка перевіряє опубліковані дані щохвилини, після повернення у вкладку або відновлення мережі; є кнопка «Оновити дані». Кнопка перечитує сайт, а не запускає збір Telegram. Успішне завантаження старого знімка не змінює час перевірки каналу. Свіжість перераховується за годинником користувача кожні 15 секунд, навіть при збоях мережі.
- Якщо Telegram недоступний, запит повторюється до трьох спроб. Після невдачі або помилки розмітки запуск завершується помилкою; журнал і попередній опублікований сайт зберігаються. Старий знімок автоматично втрачає поточний стан через 15 хвилин.
- Розклад Actions не гарантує точного інтервалу. Для гарантованого опитування потрібен окремий постійний збирач або зовнішній планувальник; поточний сайт чесно показує затримки, а не продовжує стан безстроково.

Перший запуск після клонування нічого не потребує: журнал уже в репозиторії. Повністю перебудувати його з експорту Telegram Desktop можна так: `node tools/fetch-telegram.js --seed result.json`.

## Запуск локально

Потрібен Node.js 20 або новіший. Зовнішніх npm-залежностей немає; Leaflet 1.9.4 (BSD-2) лежить у `assets/vendor/`.

~~~sh
npm run fetch   # дочитати нові пости каналу
npm start       # зібрати _site/ і відкрити http://127.0.0.1:4173
~~~

Інший порт: змінна середовища PORT. Автономний `_site/electricity_dashboard_standalone.html` відкривається подвійним кліком і приймає JSON-файли.

## Публікація

1. Settings → Pages → Source: **GitHub Actions**.
2. Actions → «Update data and deploy» → Run workflow (або дочекатися планового запуску).

Workflow потребує прав `contents: write` (комітить журнал) і `pages: write`.

## Розширена аналітика

- Імпорт кількох Telegram-експортів або архівів Light Stat, до 50 МБ на файл у браузері.
- Початковий період — останні 30 календарних днів доступного архіву. Є 7 / 90 днів, весь архів та власні дати.
- Календар «день × година», точні інтервали, походження даних, клавіатурна навігація стрілками. Великі періоди переглядаються сторінками по 30 днів.
- Порівняння локацій за часом без світла, повнотою даних або назвою.
- CSV поточної вибірки, JSON повного результату та об’єднаний архів для повторного імпорту.

## CLI

~~~sh
node analyze_electricity.js
node analyze_electricity.js --days 30
node analyze_electricity.js first.json second.json --days 7 --output merged.json
node analyze_electricity.js data/events.json --from 2026-01-01 --to 2026-01-31 --output january.json
~~~

Без файлів аналізується data/events.json. Без параметрів періоду — весь архів. --days відраховується від кінця архіву, **не від сьогодні**. Дата --to включає весь обраний день у Europe/Kyiv. Внутрішні інтервали напіввідкриті: [початок, кінець). Максимальне вікно — 10 років.

Результат записується до electricity_analysis.json або electricity_analysis_Ndays.json у поточній директорії. --output змінює шлях; перезапис вхідного архіву заборонено.

## Як рахується історія

Єдиний модуль lib/electricity.js використовується CLI та браузером.

1. Telegram: пріоритет має date_unixtime; текст підтримує рядки та rich-text фрагменти. Локальні дати розбираються в Europe/Kyiv, незалежно від часового поясу комп’ютера.
2. Ідентичність точки — пара sourceId + pointId. Однакові sg30 у різних джерелах не об’єднуються. Для Telegram використовується id каналу; за його відсутності — ім’я архіву й назва каналу.
3. Події сортуються до обрізання періоду, тому враховується стан перед його початком. Однакові події в однаковий момент не подвоюють час. Суперечливі стани в один момент дають невідомий інтервал.
4. Журнал event-log реконструює стан **тільки між сусідніми подіями**. Це припущення про повноту журналу між записами, а не підтвердження безперервних вимірювань. Період до першої події невідомий. Після останньої події стан продовжується лише до observedUntil джерела (час, коли журнал перевірено повністю) і не довше 30 днів тиші; без observedUntil — невідомий. Відомі розриви позначаються подіями unknown.
5. Вимірювання observations чинне до validUntil або maxAgeSeconds (типово 120 секунд), але не пізніше наступної події. Після закінчення актуальності стан невідомий. TTL — договір джерела, а не оцінка точності датчика.
6. evidence: connectivity завжди дає невідомий стан живлення. Мережевий збій не прирівнюється до відключення. Графіки schedules зберігаються окремо й не впливають на фактичні години.
7. Кількість вимкнень — відомі переходи on → off у вибраному періоді. Початкове off без попереднього on не рахується як відомий початок. Остання подія off може позначити початок вимкнення, навіть коли його тривалість ще невідома.
8. Сума onHours + offHours + unknownHours дорівнює тривалості вікна. Добові тривалості можуть бути 23 / 25 годин при зміні часу. availability — частка on серед відомого часу; coverage — частка відомого часу в усьому вікні. Їх не можна підміняти одне одним.

Старе поле avgHoursPerDay збережене як **еквівалент за 24 години всього вікна**: 24 × on / duration. Невідомий час не приписується до off; цей показник є нижньою оцінкою, якщо coverage < 1. Інтерфейс показує реальні тривалості замість цього нормованого показника. Середні по точках не зважені за населенням і не є міською статистикою.

## Формат власного джерела

~~~json
{
  "schemaVersion": 1,
  "sources": [{"id": "house-sensor", "name": "Датчик будинку", "kind": "observations", "method": "mains-sensor", "maxAgeSeconds": 120}],
  "points": [{"sourceId": "house-sensor", "id": "input-a", "name": "Ввід А", "address": null, "district": null, "supplyLine": "А", "coordinates": null}],
  "events": [
    {"sourceId": "house-sensor", "pointId": "input-a", "timestamp": "2026-02-01T08:00:00+02:00", "state": "on", "evidence": "measured"},
    {"sourceId": "house-sensor", "pointId": "input-a", "timestamp": "2026-02-01T08:01:00+02:00", "state": "off", "evidence": "measured"}
  ]
}
~~~

Для журналів використовуйте kind: event-log; evidence типово reconstructed. Для observations явно вкажіть evidence: measured / connectivity / reconstructed. timestamp і validUntil приймають ISO 8601 або Unix-час **у мілісекундах**; в Telegram date_unixtime має секунди. Для неоднозначних місцевих годин при переході DST потрібен явний зсув або Unix-час.

Координати: {"lat": 50.45, "lon": 30.52}, лише якщо місце справді перевірене. Адреса, район, ввід і координати необов’язкові. Інтерфейс не геокодує та не вгадує їх. Кілька вводів мають окремі pointId. Спостереження різних джерел не голосують за єдиний стан будинку.

Імпорт відхиляє некоректну структуру джерел; некоректні окремі події пропускає з діагностикою. Повторний імпорт файлу з тим самим ім’ям замінює його в поточній сесії. Дані з різними іменами зливаються, однакові події дедуплікуються під час аналізу.

## Результат і сумісність

Вихідний JSON тепер має schemaVersion: 2. Числові поля — числа, не рядки. Основні поля групи: sourceId, id, key, onHours, offHours, unknownHours, measuredHours, reconstructedHours, coverage, availability, outageCount, longestOutageHours, intervals. dateRange містить точні UTC-межі, timeZone — Europe/Kyiv. diagnostics показує дублікати, конфлікти та пропущені записи.

Старі JSON-звіти не є вхідними архівами: імпортуйте початкові події. Старі HTML-адреси збережені на сайті. Результати CLI (electricity_analysis*.json) у репозиторій не комітяться; попередні рейтинги з понад 24 годинами на добу недійсні.

data/summary.json сайту (schemaVersion 1): counts, windows (day / week / month — ковзні 24 год, 7 і 30 днів до observedUntil) і groups з полями state, active, since, lastEvent, addresses, day / week (метрики + intervals як [початок мс, кінець мс, стан]) та month.

## Розробка та перевірка

~~~sh
npm test
npm run build
npm run test:browser
~~~

build-site збирає _site/: головну карту, explore.html, старі адреси electricity_dashboard.html та автономний electricity_dashboard_standalone.html, а також data/summary.json. Не редагуйте _site вручну. Browser-тест сам збирає сайт, запускає локальний сервер і headless Chrome/Edge з окремим профілем у .cache/ та зберігає скриншоти в .cache/qa/. Потрібен Chrome/Chromium/Edge; шлях можна вказати через CHROME_PATH. На обмежених Windows runner використовується окремий headless-профіль без sandbox. Особисті браузерні профілі не використовуються.
